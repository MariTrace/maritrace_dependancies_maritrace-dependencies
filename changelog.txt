0.0.4

- Add micrometer via micrometer-bom 1.15.12.
- Reason: micrometer-core was the single largest uncovered source of Maven alerts
  (26 open, all high - GHSA-g3pr-3p32-fp23 / CVE-2026-40984, HTTP server
  instrumentation DoS) across 26 repos.

- THIS RELEASE REQUIRES A PAIRED SOURCE CHANGE. Do not bump a service to 0.0.4
  by version alone - it will fail to compile.

  The advisory has NO in-line patch: the 1.13.x and 1.14.x lines are vulnerable
  through their final releases (1.13.15, 1.14.14), so clearing it needs a MINOR
  jump to 1.15+. Micrometer 1.13 moved the Prometheus registry onto the new
  Prometheus Java client, renaming the package:

      io.micrometer.prometheus.*  ->  io.micrometer.prometheusmetrics.*

  Every affected service must have its imports rewritten in the same commit:

      sed -i '' 's/io\.micrometer\.prometheus\./io.micrometer.prometheusmetrics./g'

  Verified on data-services/maritrace-ais-streamer: 3 import lines across 2 files,
  after which it compiles clean. All other usage is io.micrometer.core.instrument.*,
  which is unchanged. No service uses the legacy io.prometheus.client API, so there
  is no push-gateway or collector migration to do.

  bump-bom-version.py applies this rename automatically when moving to 0.0.4 or
  later, so the two cannot be separated by accident.

0.0.3

- Add five libraries: org.json:json 20250517, commons-lang3 3.20.0, gson 2.14.0,
  zookeeper 3.9.5, junit 4.13.2.
- Reason: after the estate-wide rollout, the remaining open Dependabot alerts had
  concentrated almost entirely in libraries this BOM did NOT manage. On
  nmea0183-parser the BOM cleared 32 of 35 alerts and the 3 survivors were
  org.json and commons-lang3. These five cover the rest.

- READ BEFORE BUMPING A SERVICE TO 0.0.3. Two of these cross a major boundary
  for some consumers, and this BOM does not know which:

  * zookeeper - 3 repos declare 3.4.11 (pipeline_v1 commons / data-api /
    processing_coordinator); the other 2 are on 3.8.1. ZooKeeper 3.4 -> 3.9
    crosses the 3.5 client rewrite. The client talks to a real ensemble, so
    confirm the SERVER version before bumping a live consumer. data-api is the
    only live one of the three.
  * junit - 21 declarations are still on 3.8.1 (Maven archetype default).
    4.13.2 retains the junit.framework compatibility layer, so 'extends
    TestCase' still compiles, but it is a 3.x -> 4.x jump and the runner
    differs. Test-scope only: no production exposure either way.

- The other three (org.json, commons-lang3, gson) are low-risk, backward-compatible
  jumps within a stable major line.

- Note this BOM is pinned per repo, so publishing 0.0.3 changes NOTHING until a
  repo bumps its import from 0.0.2. That is deliberate: it makes each consumer an
  opt-in decision rather than an estate-wide surprise.

0.0.2

- Raise jackson to 2.21.2 (via jackson-bom) and commons-io to 2.20.0.
- Reason: Spring Boot 4.0.5 - now used by four of the api services - already
  ships jackson 2.21.2 and commons-io 2.20.0. At the old pins the BOM was
  BEHIND the platform, so importing it into those services would have
  DOWNGRADED both libraries. A BOM that lowers a version is worse than no BOM.
- Principle going forward: this BOM must only ever raise a version, never
  lower one. Before adopting it in a service, compare its pins against what
  that service already resolves (mvn dependency:list) - Spring Boot moves
  faster than this file, so the check has to be repeated, not assumed.
- postgresql (42.7.12), kafka-clients (3.9.2), log4j (2.25.4) and guava
  (33.4.8-jre) are unchanged - all already at or above what Boot 4.0.5 ships.
